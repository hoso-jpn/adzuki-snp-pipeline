# 受託データ取扱い前提(Issue #26)

Issue #26は「データ転送、保持期間、削除、外部AIサービス非送信に関する受託時の前提を文書化する」
ことを明示的な完了条件の一つとしている。本文書はその前提を記録するものであり、特定の顧客・
案件に紐づく契約条件そのものではない。個々の受託案件では、本文書に記載する原則を満たす範囲で、
案件ごとの契約書・NDA・SOWが優先する。

このリポジトリ自体には顧客データも受託成果物も一切含まれない
([データ取扱いポリシー](../README.md#データ取扱いポリシー)を参照)。本文書は、このパイプライン
コードを使って顧客の実データを処理する際に、実務としてリポジトリの外側で満たすべき前提を
定めるものであり、パイプラインのコードや設定そのものを変更するものではない。

## 1. データ転送

顧客の生データ(FASTQ、BAM、VCF等)の転送手段は、案件ごとに顧客と合意した方法を用いる。
このリポジトリおよびこのドキュメント自体は、特定の転送手段(例: SFTP、顧客側クラウド
ストレージへの直接アクセス、暗号化した物理媒体)を規定しない。案件開始前に、少なくとも
以下を転送方法として明記し、顧客の承認を得る。

- 転送先(ホスト、リージョン、アクセス制御)
- 転送経路の暗号化方式
- 転送完了後の送信元データの扱い(削除するか、顧客側で保持するか)

パイプライン自体は、`--input`/`reference_fasta`等のパラメータで既にローカルまたは案件専用の
storageに存在するファイルパスを受け取るのみであり、ダウンロード・アップロードの自動化機構は
持たない(実データ検証で用いた[実データコホートE2E検証](../README.md#実データコホートe2e検証issue-26)
の公開WGSデータのダウンロードも、案件専用の受託ワークフローではなく、このリポジトリ自身の
検証目的でSeedcore-01のscratch領域に対して手動で行ったものであり、顧客データの転送手順の
実例ではない)。

## 2. 保持期間(Retention)

顧客データの保持期間は、契約・案件ごとに顧客と合意した期間を適用する。本文書はデフォルトの
保持期間を規定しない。案件開始前に、少なくとも以下を保持期間として明記する。

- 生データ(FASTQ等)の保持期限
- 中間成果物(BAM、gVCF、GenomicsDBワークスペース等)の保持期限。多くの場合、生データより
  短い期間で削除して差し支えない
- 最終成果物(VCF、QCレポート、GSパネル、run manifest等)の保持期限。契約上の納品物としての
  保持義務が生データ・中間成果物と異なる場合がある

## 3. 削除

解析終了後の削除は、以下を満たすことを前提とする。

- 削除の実施時期を、案件ごとの保持期間(上記2.)の満了時点、または顧客からの削除要求受領時点
  のいずれか早い方とする
- 削除は生データ・中間成果物・最終成果物のすべてを対象とし、Seedcore-01等の実行環境の
  scratch領域・Nextflowの`work`ディレクトリ・`-with-trace`/`-with-report`等の実行ログを
  含む(実行ログにはサンプルIDやファイルパスが記録され得るため、生データそのものでなくとも
  削除対象に含める)
- 削除の実施を、削除日時・削除対象・削除実施者を記録した確認記録(削除ログ)として残す。
  確認記録自体は顧客の生データを含まないため、必要であれば納品物と分離して保持してよい
- 契約上、顧客自身による削除確認(例: 削除完了報告書への確認)が求められる場合は、その手順に
  従う

このリポジトリ自身の実データ検証(Issue #8 Phase 5、Issue #11、Issue #26)で使用した
scratch領域上のデータは、公開データのみであり、上記の削除前提の対象ではない。ただし、公開
データであっても、検証終了後にリポジトリへcommitされることはない([データ取扱いポリシー](../README.md#データ取扱いポリシー)参照)。

## 4. 外部AIサービスへの非送信

顧客のFASTQ・BAM・VCF・遺伝子型行列等の生データおよび中間成果物は、外部の大規模言語モデル
(LLM)・外部AIサービス(このリポジトリの開発・保守作業で使用するAIコーディングアシスタントを
含む)へ送信しない。

- パイプライン自体はローカル(顧客の環境またはSeedcore-01のような自社管理下の実行環境)で
  完結し、外部APIへの生データ送信を行う処理は含まれていない
- 本開発・保守作業でAIコーディングアシスタントを使用する場合、それらのツールに顧客の実データ
  そのもの(ファイル内容)を渡さない。パイプラインコード・設定・synthetic fixture・チェックサム
  やレコード件数のような集計値(本文書や`docs/real_cohort_e2e_run_manifest.json`のような
  provenance manifest)のみを扱う
- 上記の原則に対する例外(たとえば、顧客サポートのため特定のエラーメッセージやログの断片を
  外部サービスへ共有する必要が生じた場合)は、事前に顧客の明示的な承認を得ることを前提とする。
  暗黙の同意や事後報告では代替しない

## 5. 例外時の顧客承認

上記1.〜4.のいずれかについて、案件の事情により異なる取り扱いが必要な場合(例: 顧客指定の
転送手段、契約上の特別な保持期間、外部サービスとの連携が必要な特殊な検証)は、その内容を
文書化した上で顧客の明示的な承認を得てから実施する。承認なしに、本文書に記載した前提から
逸脱しない。

## このリポジトリの範囲との関係

本文書が定める前提は、このリポジトリのコード・テスト・CIには反映されていない運用ルールである
(反映しようがない: 転送手段や保持期間は案件ごとに異なり、削除は実行環境側の操作であるため)。
このリポジトリ側で機械的に保証できるのは、[データ取扱いポリシー](../README.md#データ取扱いポリシー)
に記載の通り、生データ・顧客データがGitにcommitされないことのみである。本文書はその機械的
保証と、受託案件運用側の人的・契約的なプロセスとの間のギャップを明示するために存在する。
