# BUILD_GS_PANEL streaming benchmark (Issue #44)

## What this measures, and what it does not

This document records the bounded-memory rewrite of `bin/build_gs_panel.py`
(Issue #44) measured against **synthetic cohorts**, not against Issue #33's real
10/20-sample GS PASS artifacts.

Those real artifacts were produced on host `seedcore-01` and are recorded in
`real_cohort_scale_validation_10sample_manifest.json` and
`real_cohort_scale_validation_20sample_manifest.json`. They are **not present on
the machine this work was carried out on** (`a5-pro`): no
`cohort_gs.snp.pass.vcf.gz` outside this repository's own small nf-test fixtures
exists on any mounted filesystem, and the only other mounted volume
(`/mnt/data`, 1.8 TB) is empty. In line with Issue #44's own instruction not to
re-download or re-derive large cohorts, no attempt was made to reproduce them.

**Issue #44's real-data completion criterion ("10/20-sample real artifact
equivalence with the old output", "20-sample peak RSS measured") is therefore
NOT met by this document.** What follows is scaling evidence on generated input;
it demonstrates the memory complexity change and byte-level output equivalence,
but it is not a substitute for a replay against the real cohorts, which should
be run on `seedcore-01` before this work is treated as fully validated.

### How memory was measured

The number reported below is **the builder process's own peak RSS**
(`/usr/bin/time -v`, "Maximum resident set size"), for the Python process alone.
It is not a cgroup figure, not a container peak, and does not include page cache
charged for the input or the five outputs. Issue #33's 19.88 GiB figure for this
process is a *cgroup* peak and is not directly comparable to these numbers.

One measurement pitfall is worth recording because it produced a convincing
false result during development. On Linux `ru_maxrss` is carried across
`fork`/`exec`, so a child spawned from a parent that had already grown large
reports the *parent's* high-water mark. Measuring the builder from a harness
that had itself materialized the test VCF made a bounded implementation look
like it was growing linearly (108 MiB "peak" at 320k variants, versus 20.6 MiB
when measured from a small shell). Every figure here is therefore taken from a
run launched directly by `/usr/bin/time` from a small shell, and the unit test
that guards this property samples `/proc/<pid>/statm` instead of reading
`ru_maxrss`.

Swap was sampled from `/proc/meminfo` (`SwapTotal - SwapFree`) immediately
before and after each run.

## Results

Old = `main@cc2c5ca`'s `bin/build_gs_panel.py`. New = this branch. Both run over
the identical generated input, on the same machine, back to back.

| Variants x samples | Old peak RSS | New peak RSS | Reduction | Old wall | New wall | Speedup | Swap delta |
| --- | ---: | ---: | ---: | ---: | ---: | ---: | ---: |
| 250,000 x 20 | 531,156 KiB (518.7 MiB) | 21,348 KiB (20.8 MiB) | 95.98% | 49.4 s | 19.0 s | 2.60x | 0 kB |
| 1,000,000 x 10 | 1,516,872 KiB (1.45 GiB) | 20,636 KiB (20.2 MiB) | 98.64% | 100.2 s | 44.8 s | 2.24x | 0 kB |
| 1,000,000 x 20 | 2,093,092 KiB (2.00 GiB) | 21,336 KiB (20.8 MiB) | 98.98% | 205.9 s | 77.2 s | 2.67x | 0 kB |
| **4,000,000 x 20** | **8,347,516 KiB (7.96 GiB)** | **21,496 KiB (21.0 MiB)** | **99.74%** | 770.0 s | 280.3 s | 2.75x | 8 kB |

The old implementation grows almost exactly linearly in the variant count
(2.00 GiB at 1M, 7.96 GiB at 4M, both at 20 samples). The new one moves by
160 KiB across the same 4x — and by 860 KiB across the whole 16x range from
250k to 4M — which is allocator noise, not retention.

The speedup is a side effect, not a goal: the old code classified every genotype
five times (once per output, plus a second accounting pass to build the summary)
and the new one classifies each exactly once.

Swap was untouched at every scale (the single 8 kB delta at 4M is unrelated
background activity, and appeared during the *old* run).

### The gzip representation did not change

Issue #44's review established that this could not be assumed. It cannot:
`gzip.compress(payload, mtime=0)` delegates to zlib's gzip wrapper and writes
`OS=3`, while `gzip.GzipFile` — the obvious streaming replacement — writes
`OS=255`. Measured directly: same decompressed bytes, different file.

Streaming through `zlib.compressobj(9, zlib.DEFLATED, 31)` uses that same zlib
wrapper, and deflate's output does not depend on input chunking absent a forced
flush. Verified byte-identical to the one-shot form across chunk sizes from 1
byte to the entire payload, at panel shapes from 0 to 50,000 variants and up to
100 samples, **on the host (zlib 1.3) and inside the pinned production image
(zlib 1.3.1)**.

So: the compressed representation is unchanged, and **previously published
matrix checksums remain valid**. No historical manifest or checksum was
rewritten by this work.

The published gzip member carries no `FNAME` and no `FCOMMENT` (the builder
writes through a hidden staging file whose absolute host path must not reach a
published artifact), and a zeroed `MTIME`. `tests/modules/build_gs_panel.nf.test`
asserts those header bytes inside the real task container.

## Limitations and follow-ups

1. **No real-data validation.** As stated at the top: Issue #33's real 10/20-sample
   artifacts are not on this machine, so the real-artifact equivalence and the
   real 20-sample peak RSS remain unmeasured. This is the outstanding item for
   Issue #44.
2. **The reconciler is now the memory bottleneck of the GS lineage.** Measured
   during this work: `reconcile_gs_panel_accounting.py` peaked at 1,953,472 KiB
   (1.86 GiB) on the 4,000,000 x 20 panel, because it materializes the full
   ordered tuple of variant keys from each artifact in order to compare identity
   and order. That is outside Issue #44's scope (which is `BUILD_GS_PANEL`), and
   it is not a regression — but with the builder down to 21 MiB it is now the
   largest Python consumer in this lineage and deserves its own issue.
3. **Absolute wall times are not comparable to Issue #33's**, which were measured
   on different hardware (`seedcore-01`).
4. **Python RSS only.** Container/cgroup peaks, which include page cache charged
   for the input and the five outputs, were not measured here and remain the
   basis of the resource contract in `nextflow.config`. No resource allocation
   was changed by this work.
5. **Publication is not a five-file transaction.** See
   `docs/gs_panel_data_contract.md`, "Output publication and failure semantics",
   for exactly what is and is not guaranteed.
