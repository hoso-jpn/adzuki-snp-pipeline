# Mapping resource profile: real reference, real WGS data (Issue #8 Phase 5)

This document records Issue #8 Phase 5: a real-reference, real-FASTQ, real-hardware
measurement of `BWA_MEM2_INDEX` and `BWA_MEM2_MEM_SORT` as implemented by PR #25
(Phase 1-4), so that the CPU-split and memory-split formulas documented in README and in
`modules/local/bwa_mem2_mem_sort.nf` can be evaluated against something other than the
synthetic test fixture. It is a measurement of one run, on one machine, against one real
dataset -- not a performance guarantee, not a production SLA, and not a validation of
20-30-sample or 327-sample cohort scale (that is Issue #11's and Issue #26's scope).

### A real discrepancy worth recording, not resolving by guessing

The read headers embedded in the FASTQ itself (e.g.
`@SRR29909135.1 A00609:64:H3CWYDSXY:4:1101:10393:1016/1`) encode instrument serial number
`A00609`, flowcell `H3CWYDSXY`, and lane `4`. Sampling the lane field across the entire R1
file confirms exactly one lane (`4`) is present -- this run corresponds to a single real
sequencing lane, matching the samplesheet's single read group below.

The `A00609` instrument-serial prefix follows the naming convention Illumina uses for
NovaSeq 6000-series instruments, not HiSeq X -- which conflicts with ENA/SRA's own
`instrument_model: Illumina HiSeq X` metadata field for this same run. This document does
not attempt to adjudicate which of the two sources is correct; both are recorded above
exactly as obtained, and this discrepancy is the reason `optical_duplicate_pixel_distance`
was **not** overridden for this run (see below) rather than set to a patterned-flowcell
value on the strength of either source alone.

## `optical_duplicate_pixel_distance`: what could and could not be justified

The exact pinned `GATK 4.6.2.0` container this pipeline uses for
`GATK_MARKDUPLICATES` was run directly (`docker run ... gatk MarkDuplicates --help`) to
read its own primary documentation for this parameter, rather than relying on a
web page:

> `--OPTICAL_DUPLICATE_PIXEL_DISTANCE <Integer>` The maximum offset between two duplicate
> clusters in order to consider them optical duplicates. The default is appropriate for
> unpatterned versions of the Illumina platform. For the patterned flowcell models, 2500
> is more appropriate. For other platforms and models, users should experiment to find
> what works best. Default value: 100.

This confirms *that* patterned flowcells warrant a different value, but classifying
`SRR29909135`'s own flowcell as patterned or unpatterned depends on which of this run's
two conflicting instrument identifications (SRA's "HiSeq X" vs. the read header's
NovaSeq-pattern serial number `A00609`) is correct -- and this session could not
independently resolve that conflict from a verified primary source. Given that unresolved
discrepancy, **this run used the pipeline's existing default (`100`), unmodified**, rather
than guess at `2500` from either metadata source alone. This is a data-provenance
limitation of this specific accession, not a finding that `100` is the generally correct
value for this pipeline's other, better-identified inputs -- a future real cohort with an
unambiguous instrument identification should re-derive this parameter from its own
metadata rather than inherit this run's choice by default.

## Run command

```bash
NXF_VER=26.04.6 nextflow run . \
  -profile docker \
  -c real_reference.config \
  --input samplesheet.csv \
  --outdir results/ \
  --enable_gs_panel false \
  -w work/ \
  -with-trace metrics/trace.txt \
  -with-timeline metrics/timeline.html \
```

`real_reference.config` sets `reference_fasta` to the FASTA above (and leaves
`reference_fai`/`reference_dict`/`bwa_index_prefix` as `null`, so `SAMTOOLS_FAIDX`,
`GATK_CREATE_SEQUENCE_DICTIONARY`, and `BWA_MEM2_INDEX` all run -- the generated-index
path). `-profile docker` was used **without** the `test` profile, since `conf/test.config`
overrides `process_mapping`/`process_bwa_index` down to 2 CPUs / 4 GB -- this measurement
needed the real production resource contract (`process_mapping`/`process_bwa_index`:
8 CPUs, `16.GB * task.attempt`, from `nextflow.config` directly), not the CI-sized
override. `--enable_gs_panel false` was set because a 1-sample GS panel is not a
meaningful exercise of that lineage and is out of this Issue's scope (Issue #18/#20
already cover the GS panel contract on synthetic data). This host is Linux/AMD64 natively,
so the `docker_amd64` (Apple Silicon emulation) profile was correctly not used.

The observed thread split (`bwa-mem2 -t 7` / `samtools sort -@ 1`) and per-thread sort
memory (`7680M`) match the documented formula exactly for `task.cpus=8`,
`task.memory=16 GiB`: `sort_threads = max(1, floor(8*0.2)) = 1`, `bwa_threads = 8-1 = 7`;
`bwa_share_mib = floor(16384*0.5) = 8192`, `os_overhead_mib = 512`,
`sort_share_mib = 16384-8192-512 = 7680`, `sort_mem_per_thread_mib = 7680/1 = 7680`.

Peak RSS (12.9 GB) leaves 3.1 GiB of headroom against the 16 GiB allocation (~19.4%
unused) -- positive, but visibly tighter than `BWA_MEM2_INDEX`'s headroom. No OOM and no
retry occurred on this run (`task.attempt` stayed at 1 throughout); this is not evidence
that a smaller allocation would also succeed, only that 16 GiB was sufficient here for
this one ~19.3x-coverage, 447.8 Mb-genome sample.

### No intermediate `.sam`, confirmed on real data

The mapping task's Nextflow work directory was inspected directly after completion (not
just the published output directory): it contains the pinned container's `.command.*`
bookkeeping files, symlinks to the reference index and trimmed FASTQ inputs, the
`bwa-mem2` stderr log, and exactly one BAM (`SRR29909135_L004.sorted.bam`). No `.sam` or
`.sam.gz` file of any kind is present. PR #25 verified this on the synthetic fixture; this
is the same guarantee confirmed for a real ~8.64 Gbp WGS sample.

## CPU split (80/20): baseline confirmed, not retuned

This run used the existing, unmodified 80/20 split (`bwa-mem2` 7 threads / `samtools sort`
1 thread on `task.cpus=8`) and completed successfully with no failure, no OOM, and no
retry. The task's overall `%cpu` (619.2% of a possible 800%) is consistent with
`bwa-mem2`'s alignment work dominating the pair's total CPU cost, as the existing
in-code/README rationale assumes, but a single baseline run does not by itself prove 80/20
is the *optimal* split -- only that it is a *safe* one for this dataset and machine. No
comparative alternative-split benchmark (e.g. 75/25, 67/33) was run: Issue #8's own
guidance is to only spend effort on such a comparison once a baseline run surfaces a clear
bottleneck (a persistently CPU-saturated `samtools sort` thread, a stalled/idle
`bwa-mem2`, or a wall-time or resource failure), and none of those was observed here.
**The 80/20 split is retained unchanged.**

## Memory formula: baseline confirmed, not retuned

The memory-split formula (50% of `task.memory` reserved for `bwa-mem2`, a fixed 512 MiB
for OS/tool overhead, the remainder divided across `samtools sort`'s own threads)
completed both `BWA_MEM2_INDEX` and `BWA_MEM2_MEM_SORT` successfully at `task.memory=16
GiB`, with positive headroom in both cases (37.5% and ~19.4% respectively) and no OOM or
retry. `BWA_MEM2_MEM_SORT`'s headroom is visibly tighter than `BWA_MEM2_INDEX`'s, which is
worth carrying forward as context for any future real-cohort resource planning (Issue
#11/#26), but a single successful run with a positive margin is not, by itself, grounds to
either raise or lower the current default. **The memory formula and the `16.GB *
task.attempt` default for `process_mapping`/`process_bwa_index` are retained unchanged.**

## Generated vs. prebuilt index path

This Phase 5 run exercised the **generated-index** path only (`bwa_index_prefix=null`),
since building the real index from the real reference at least once was itself part of
what needed measuring (`BWA_MEM2_INDEX`'s own resource profile above). The
**prebuilt-index** path -- `BWA_MEM2_INDEX` skipped entirely, mapping reading a
pre-existing index bundle instead -- is already covered by this repository's existing
automated tests (`tests/modules/bwa_mem2_mem_sort.nf.test`'s prebuilt-index test and
`tests/pipeline/adzuki_snp_pipeline.nf.test`'s equivalent pipeline-level test), both on the
synthetic fixture; re-running the ~24-minute real-data mapping step a second time solely
to re-exercise a code path already covered by real-container nf-tests was judged not to add
new evidence proportionate to its cost, so it was not repeated here against the real
reference.

## Downstream stages: not required for, and not claimed by, this Issue

Per Issue #8's own scope, this Phase 5 measurement's primary target is
`BWA_MEM2_INDEX`/`BWA_MEM2_MEM_SORT` alone; completing cohort-scale Joint Genotyping is
Issue #11's and Issue #26's responsibility, not this one's. `SAMTOOLS_MERGE`,
`GATK_MARKDUPLICATES`, `SAMTOOLS_INDEX`, and `SAMTOOLS_QC` were allowed to continue
running on this same real sample as a bonus, best-effort check of
read-group/duplicate-marking behavior beyond the mapping step alone -- this is **not**
treated as validation of 20-30-sample or 327-sample cohort scale, GenomicsDBImport
batching, or any other Issue #11/#26 concern.

`GATK_MARKDUPLICATES` (real data, `optical_duplicate_pixel_distance=100`, the unmodified
default -- see above): `PERCENT_DUPLICATION=0.100031` (~10.0%), `READ_PAIR_DUPLICATES`
2,823,165, `READ_PAIR_OPTICAL_DUPLICATES` 0, `ESTIMATED_LIBRARY_SIZE` 132,354,794. This
duplication rate is consistent with -- not identical to, given the different
tools/trimming already noted above -- the historical pilot's documented "~10%" duplicate
rate (README's "Single-Sample Pilot Results"). Zero optical duplicates were called at
`--OPTICAL_DUPLICATE_PIXEL_DISTANCE 100`; this is not, by itself, evidence for or against
overriding to `2500` given the unresolved instrument-identification discrepancy above --
a larger distance would need to be tested to know whether it would reclassify any of this
library's PCR/sequencing duplicates as optical, and that comparison was not run here.

Whether `GATK_HAPLOTYPECALLER` and the remaining Joint-Genotyping-through-QC stages
completed by the time this PR was opened is reported in the PR description itself, not
here -- this document's own scope is the mapping stage, and its conclusions above do not
depend on what happens after `SAMTOOLS_QC`.

## Conclusion

Both of Issue #8's Phase 5 primary measurement targets -- `BWA_MEM2_INDEX` and
`BWA_MEM2_MEM_SORT` -- completed successfully against the real Longxiaodou 4 reference and
a real ~19.3x-coverage WGS accession, using the unmodified production resource contract
(`process_bwa_index`/`process_mapping`: 8 CPUs, 16 GiB), with positive memory headroom in
both cases and no OOM, retry, or `.sam` intermediate. No tuning was applied: this is a
documented technical judgment (Issue #8's own stated priority is not changing code for its
own sake), not an oversight. The 80/20 CPU split and the memory-split formula PR #25
introduced as unmeasured starting assumptions are, as of this document, **measured and
confirmed safe for this one real reference and this one real accession on this one
machine** -- not proven optimal, and not a performance guarantee for any other reference,
accession, or hardware.
